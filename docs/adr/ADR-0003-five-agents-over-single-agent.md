# ADR-0003: 五 Agent 架构而非单一 Agent

> **状态：** 已采纳
> **日期：** 2026-07-11
> **决策者：** 陈家智（AI Architect）

---

## 背景

"用户输入 → 给出音乐"这个需求，用一个 Agent（一个 Prompt）也可以完成。为什么要拆成五个？

## 决策

**将系统拆分为五个职责独立的 Agent，不采用单一 Agent 方案。**

## 理由

1. **职责分离（Separation of Concerns）：**
   - ①只做信息采集、②只做中医辨证、③只做知识映射、④只做 API 调用、⑤只做反馈收集
   - 每个 Agent 出错时可独立排查，单一 Agent 出错时不知道是哪个环节的问题

2. **可独立替换：**
   - 换一个大模型 → 只影响需要 LLM 的 Agent（②③⑤）
   - 换一个音乐平台 → 只影响④
   - 换一个评价体系 → 只影响⑤
   - 单一 Agent 方案：换任何东西都要改整个 Prompt

3. **可解释性：**
   - 用户问"为什么推荐角调？" → ②的 `reason` 字段可以追溯到《黄帝内经》
   - 用户问"为什么 BPM 是 68？" → ③的 `reason` 字段可以追溯到 RCT 文献
   - 单一 Agent 方案：只有一个输出，没法逐环节解释

4. **论文写作便利：**
   - 五个 Agent = 五个子系统 = 论文中五节内容
   - 每个 Agent 的性能可独立评估

5. **人类专家可介入：**
   - ③处方Agent 的输出（处方JSON）可以人工审核后再发给④
   - ⑤反馈Agent 的决策（继续/微调/重辨证）可以人工确认
   - Human-in-the-Loop 在单一 Agent 中无法实现

## 后果

- **正面：** 架构清晰，可调试，可替换，可解释。
- **正面：** 每个 Agent 复杂度可控，团队成员可并行开发。
- **负面：** Agent 间通信（链式调用）增加整体延迟。但本项目的 5 个 Agent 是串行执行（非并发），总延迟 = sum(各 Agent 延迟)，预计 3-10 秒，用户可接受。
- **负面：** LangGraph 图定义更复杂。但这是值得的复杂度。
