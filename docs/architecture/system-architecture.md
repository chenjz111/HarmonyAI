## 前言：项目定位升级

### 之前的定位

> 做一个 AI 音乐 APP

### 现在的定位

> **构建一个基于中医知识驱动的 AI 音乐干预决策系统。**
>
> APP 是展示形式，AI 音乐是输出结果。
> 真正的核心技术是中间那套 **"中医知识 → 音乐参数 → AI 生成"的决策引擎**。

### 命名规范（全项目统一）

| ❌ 禁止使用 | ✅ 统一使用 |
|------------|------------|
| 音乐治疗 | AI 音乐辅助调理 / AI 音乐健康管理 |
| 治疗 | 干预 / 调理 / 辅助改善 |
| 疗效 | 效果 / 反馈 |
| 诊断 | 评估 / 辨证分析 |
| 病人 | 用户 |

> **原因：** 项目不构成医疗器械，参赛时评委中的医学老师会追问"你怎么证明能治疗"。使用"调理/干预/辅助"等术语，既合规又安全。

## 二、各Agent详细设计

### 2.1 ① 评估Agent —— 信息采集与量化

**输入渠道：**

| 渠道 | 处理方式 | 说明 |
|------|----------|------|
| 西医病例 | OCR(PaddleOCR) → NER(Qwen2.5-7B) → 西医→中医映射表 → 情绪量化 | 50-100组预设映射 + LLM扩展 |
| 中医病例 | OCR/文本/语音 → Qwen2.5-7B 直接提取证候 → 结合知识库 | 更简化 |
| 问卷自评 | 30题 Likert 5级量表（情绪12题 + 睡眠8题 + 身体10题） | 评分自动计算 |

**输出（统一健康画像）：**

```json

    "assessment_time": "2026-07-11T10:00:00Z"
  }
```

### 2.2 ② 中医辨证Agent —— 中医推理与可信度

**核心变化：每条输出带 confidence 分数。**

**输入：** 用户健康画像（来自①）

**处理逻辑：**

1. 情绪五维排序 → 确定主导情绪（最高分）
2. 主导情绪 → 规则引擎查五行归属（硬编码，不受LLM幻觉影响）
3. 结合RAG知识库检索相似证候案例
4. LLM（Qwen2.5-7B）综合判断 → 输出证型
5. **计算可信度**（基于：文献匹配度 × 规则引擎一致性 × LLM置信度）

**输出：**

```json
{
  "syndrome_analysis": {
    "primary_syndrome": "肝郁化火",
    "secondary_syndromes": ["阴虚", "心神不宁"],
    "primary_element": "木",
    "primary_organ": "肝",
    "primary_emotion": "怒",
    "confidence": 0.71
  },
  "confidence_breakdown": {
    "rule_engine_match": 0.85,
    "llm_confidence": 0.72,
    "literature_support": 0.65,
    "overall": 0.71
  },
  "warning": null
}
```

**低可信度处理：**

| confidence | 处理策略 |
|------------|----------|
| ≥ 0.70 | 正常进入处方Agent |
| 0.40 - 0.70 | 标记为"仅供参考"，处方Agent降权处理 |
| < 0.40 | **触发提醒：** "建议咨询专业中医师进行人工辨证" |

### 2.3 ③ 音乐处方Agent —— 开方子

> **一句话：中医师开药方。把中医语言翻译成音乐语言。它不给用户听音乐——它只给一张"药方"。**

**这是整个系统的核心创新。内部包含7个子模块（串行执行）：**

```
③ 音乐处方Agent
    │
    ├── 子模块1：RAG知识库检索
    │   （四层知识库：经典文献 + 现代论文 + 专家经验 + 用户反馈）
    │
    ├── 子模块2：五行/五音权重映射
    │   （不固定1对1，输出概率分布：角:0.75, 宫:0.15, 羽:0.10）
    │
    ├── 子模块3：调式与乐器选择
    │   （主调+辅调+推荐乐器组合）
    │
    ├── 子模块4：BPM与时长规划
    │   （根据调式和证候严重程度动态调整）
    │
    ├── 子模块5：Prompt模板引擎
    │   （模板 + 参数 → 自动组装Prompt，不直接写死）
    │
    ├── 子模块6：可信度评分
    │   （每步映射带confidence）
    │
    └── 子模块7：推荐理由解释
        （引文献原文，告诉用户"为什么推荐这个处方"）
```

#### 子模块2：五行/五音权重映射（关键创新）

**不采用固定映射，而是概率权重：**

| 证型 | 角(Mi/木/肝) | 徵(Sol/火/心) | 宫(Do/土/脾) | 商(Re/金/肺) | 羽(La/水/肾) | 策略说明 |
|------|-------------|---------------|-------------|-------------|-------------|----------|
| 肝郁化火 | **0.75** | 0.05 | 0.15 | 0.00 | 0.05 | 角调为主疏肝，宫调护脾(木克土) |
| 心火上炎 | 0.10 | **0.60** | 0.05 | 0.00 | 0.25 | 徵调为主养心，羽调克火(水克火) |
| 脾虚思虑 | 0.15 | 0.05 | **0.70** | 0.00 | 0.10 | 宫调为主健脾，角调生土(木生土) |
| 肺气虚 | 0.00 | 0.05 | 0.10 | **0.75** | 0.10 | 商调为主润肺，宫调生金(土生金) |
| 肾阴不足 | 0.05 | 0.00 | 0.05 | 0.10 | **0.80** | 羽调为主滋肾，商调生水(金生水) |

> **为什么用权重而非固定映射：**
> - 中医五音疗法本身就有"生克选调"机制——同一个证型可能有主调+辅调+克调
> - 权重网络让系统有了"AI味"——可以根据反馈数据持续优化权重
> - 答辩时可说："我们不是写死的规则，而是一个可学习的知识映射网络"

```
用户看到的内容：

🎵 推荐处方
  主调：角调式（Mi为主音），权重 75%
  辅调：宫调式（Do为主音），权重 15%
  策略：木克土，用宫调护脾胃，防肝病传脾

```

#### 子模块1：四层知识库

**设计原则：每一条知识都有出处。无论是推荐乐器、调式还是BPM，都能追溯到具体的文献或数据来源。**

```
四层知识库
    │
    ├── 第一层：经典中医文献（理论根基）
    │   ├── 《黄帝内经》素问篇、灵枢篇
    │   ├── 《伤寒论》
    │   ├── 《难经》
    │   ├── 《金匮要略》
    │   └── 《景岳全书》
    │   用途：五行五音映射的核心理论依据
    │   检索优先级：最高（硬约束）
    │
    ├── 第二层：现代研究论文（学术支撑）
    │   ├── 近五年五音疗法临床研究
    │   ├── 五行音乐疗法 RCT 报告
    │   ├── 中医体质学论文
    │   └── 《山东中医杂志》等期刊文献
    │   用途：支撑具体参数的学术依据
    │   检索优先级：高
    │
    ├── 第三层：专家经验（实践验证）  ← 新增
    │   ├── 中医师临床五音选调经验
    │   ├── 音乐治疗师处方编排经验
    │   ├── 乐器搭配的实践经验
    │   └── 疗程设计经验（如"肝郁先角调3天再转宫调"）
    │   用途：处方编排与疗程设计的实践指导
    │   检索优先级：中（需标注"经验级"，非论文级）
    │
    └── 第四层：用户反馈数据（持续进化）  ← 新增
        ├── 用户满意度数据
        ├── 证型-处方-效果关联数据
        ├── 偏好乐器/节奏统计
        └── 权重矩阵优化参数
        用途：权重网络的持续调优
        检索优先级：可选（标注"数据级"，仅用于个性化推荐）
```

**四层知识的性质差异：**

| 层级 | 性质 | 可信度 | 适用场景 | 是否硬约束 |
|------|------|--------|----------|-----------|
| 经典文献 | 文本知识 | 最高 | 五行映射规则 | ✅ 硬约束 |
| 现代论文 | 文本知识 | 高 | 参数取值范围 | ✅ 半约束 |
| 专家经验 | 隐性知识 | 中 | 处方编排策略 | ⚠ 参考级 |
| 用户反馈 | 数据知识 | 随积累升高 | 个性化推荐 | ❌ 软约束 |

> **论文写作要点：** 推荐古琴 → 出处《黄帝内经》；推荐BPM 65-75 → 出处某临床RCT研究；推荐先角调3天再转宫调 → 出处专家经验（标注来源）。所有知识可溯源，论文方法论一章直接可用。

### 2.4 ④ 音乐生成Agent —— 煎药

> **一句话：药房煎药机。拿到③的"药方"，调API煎出"药汤"（音频）。它不关心中医，它不关心Prompt写得对不对——它只管"调API，拿回音频"。**

**四级降级策略：**

```
输入（来自③）：Prompt + 参数（bpm:68, 乐器:["古筝","竹笛","古琴"]）

处理：
  尝试天工SkyMusic ──→ 成功 → 上传音频到OSS → 返回URL
     │ (失败)
  尝试MiniMax Music ──→ 成功
     │ (失败)
  尝试阿里Fun-Music ──→ 成功
     │ (全失败)
  本地五音曲库 → 找最匹配的角调曲目返回
```

**核心原则：换音乐平台时，③⑤ 完全不受影响。**

| 优先级 | 平台 | 中国乐器支持 | 状态 | 定价 |
|--------|------|------------|------|------|
| 1 | 天工 SkyMusic / Mureka | ★★★★★ 国风专精 | API已开放 | ~0.2元/首 |
| 2 | MiniMax Music 2.5+ | ★★★★★ 真实采样音源 | API完全开放 | ~1.0元/首 |
| 3 | 阿里云 Fun-Music | ★★★★ | 邀测阶段 | 未公开 |
| 4 | 本地五音曲库 | ★★★ 有限但稳定 | 无需API | 免费 |

### 2.5 ⑤ 用户反馈Agent —— 复诊

> **一句话：医生复诊。不问"好不好听"，而是问"效果怎么样"。满意的存进用户画像下次复用，不满意的返回去重新辨证或微调参数。**

| 类型 | 维度 | 收集方式 |
|------|------|----------|
| **主观** | 整体满意度 | 1-5分评分 |
| **主观** | 情绪匹配度 | 1-5分评分 |
| **主观** | 放松感受 | 1-5分评分 |
| **主观** | 睡眠改善 | 自评"是否有改善" |
| **主观** | 压力变化 | 自评"是否感觉到降低" |
| **主观** | 文字反馈 | 开放文本框 |
| **客观** | 心率(HR) | 可穿戴设备API（远期） |
| **客观** | 心率变异性(HRV) | 可穿戴设备API（远期） |
| **客观** | 睡眠数据 | 可穿戴设备API（远期） |
| **客观** | 呼吸率 | 可穿戴设备API（远期） |
| **行为** | 完整听完率 | 自动记录 |
| **行为** | 重复播放次数 | 自动记录 |
| **行为** | 使用时段 | 自动记录 |

**反馈驱动的优化策略：**

| 反馈条件 | 处理策略 |
|----------|----------|
| 满意度 ≥ 4分 | 保存该处方参数，录入用户偏好画像 |
| 满意度 = 3分 | 微调BPM/乐器配比，返回处方Agent重新生成 |
| 满意度 ≤ 2分 | 返回辨证Agent，重新评估证候 |
| 连续3天满意度 ≥ 4分 | 降低该用户的可信度阈值要求 |
| 多个用户同一证型满意度低 | 触发该证型的权重矩阵全局调整 |

### 2.6 ③④⑤ 对比：为什么必须分开

| 维度 | ③ 处方Agent | ④ 生成Agent | ⑤ 反馈Agent |
|------|------------|------------|------------|
| **一句话** | 中医师开方子 | 药房煎药机 | 医生复诊 |
| **输入** | 证型 + 可信度 | 处方JSON + Prompt | 用户评分 + 行为数据 |
| **输出** | 处方JSON + Prompt + 解释 | mp3音频URL | 优化决策（继续/微调/重辨证） |
| **关心中医吗** | ✅ 核心依赖 | ❌ 完全不管 | ⚠ 间接相关（看效果） |
| **关心音乐实现吗** | ❌ 不管 | ✅ 核心职责 | ❌ 不管 |
| **换音乐平台影响** | 无影响 | 只影响本Agent | 无影响 |
| **出错怎么排查** | 查规则引擎 + 知识库 | 查API调用日志 | 查评分数据和阈值策略 |

**揉在一起会怎样：**

| 问题 | 后果 |
|------|------|
| 音乐不好听 | 不知道是辨证错了 / Prompt没写好 / API不给力 |
| 换音乐平台 | 整个Agent要重写 |
| 优化处方逻辑 | 修改生成代码，牵一发动全身 |
| 长期满意度低 | 没法定位是哪个环节的问题 |

**分开之后：**

```
用户说"音乐不对味"
  → 查③的处方参数（调式/BPM/乐器对不对）→ 跟④无关

API挂了
  → ④内部自动降级 → ③⑤完全不受影响

想调整角调BPM范围
  → 只改③的规则表 → ④⑤代码不动

Day3反馈满意度降了
  → ⑤触发微调 → 返回③调整权重 → ④重新生成
  → 每一步都知道谁负责什么
```

## 四、参赛答辩预演

### 4.1 一句话定位

> **中医知识驱动的 AI 音乐干预决策系统。**
> 不是让 AI 猜该放什么音乐，而是让中医理论作为约束条件，驱动 AI 生成符合疗愈目标的音乐。

### 4.2 核心问答

**Q1：你们和"用 GPT 生成疗愈音乐"有什么区别？**

A：GPT 方案是"用户说焦虑 → AI 猜该放什么音乐"——黑箱。我们是：

```
用户说焦虑
  → 中医辨证为"肝郁化火"（可信度71%）
  → 知识图谱映射到 {角:0.75, 宫:0.15, 羽:0.10}
  → 规则引擎输出 BPM 68 + 古筝竹笛
  → AI 在约束下生成音乐
```

每一步有中医文献依据，每一步可追溯。

**Q2：创新点在哪里？**

A：三个层面：

| 创新维度 | 内容 |
|----------|------|
| **理论创新** | 五声音阶为主体、允许六声七声扩展，有《山东中医杂志》2024 支撑 |
| **架构创新** | 三层知识驱动架构——医学层→知识映射层→AI生成层，知识映射作为独立架构层 |
| **工程创新** | 权重映射网络（非固定规则）+ Prompt 模板引擎（参数分离）+ 可信度评分体系 + 推荐理由解释 |

**Q3：怎么保证医学有效性？**

A：我们不说"治疗"，也不声称"能治好"。我们的策略是：

- 可信度评分体系：低于 40% 建议咨询专业医生
- 推荐理由引用文献原文：每一步都有学术依据
- 反馈闭环：用户反馈持续优化权重网络
- 合规声明：定位为"辅助调理"，不构成医疗建议

**Q4：七音怎么映射五音？**

A：不暴力映射。学术文献指出五音治疗体系包含五声/六声/七声调式（《山东中医杂志》2024）。我们的方案：五声音阶为主体旋律，Fa和Si作为经过音和装饰音保留。真正决定疗愈方向的是**调式中心**，不是有没有Fa。

**Q5（预期最难）：如果用知识图谱硬编码映射，和"老中医写一个对照表"有什么本质区别？**

A：本质区别在于：
1. 我们用的是**权重网络**而非固定映射——{角:0.75, 宫:0.15, 羽:0.10}，权重可以通过用户反馈数据持续优化
2. 知识映射层结合 RAG 检索——相同证型的不同用户，可能因为体质差异得到不同的配比
3. 这是"知识驱动 AI"，不是"自动化查表"
