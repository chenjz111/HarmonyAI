# Feedback unknown-commit crash recovery — evidence and candidate

Baseline `4746858842c256497d79149cfc7efb5d20c57582`. The frozen PD009 allows a fresh experience after another listen; it does not say an event is unique. Existing schema enforces `(internal_user_pk,idempotency_key)`, not one feedback per event. R1 requires original key and original request for replay and tombstone priority.

Current POST and its internal independent-session witness can validate owner, key, fingerprint, persisted content and playback proof when the original request is still available. Public GET supports list by music and detail by feedback ID, not a key/fingerprint recovery query; deleted records are not returned from list. A missing row cannot show that an in-flight write will not commit later. Neither existing API nor process-local state can safely recover a missing original request after process death. A hash of low-entropy feedback answers is potentially sensitive, not automatically anonymous.

## Candidate requiring policy and interface review (not enabled)

1. Before sending, atomically persist a minimal owner-bound recovery handle, original opaque key, music/source/event reference and a version; never store answers, access/refresh token or reusable credential in ordinary storage. Even owner/event references are linkable personal metadata and require explicit local retention, corruption, clear-on-confirmation, backup and uninstall/reinstall rules. No unapproved fingerprint derived from answers is stored.
2. An authenticated, owner-scoped read-only operation may check the original key and stored playback association, returning only `saved`, `deleted`, or `unknown`. Query absence remains unknown until a separate approved safe finalization protocol can prove no late writer may commit. No event uniqueness constraint or silent write is introduced. Authentication failure, database errors, storage corruption, owner change, and old Guest expiry remain fail-closed; tombstones precede replay and Clear does not revive evidence.
3. Without the original body, `unknown` cannot be automatically replayed. A user-visible view must distinguish confirmed saved/deleted from unresolved, explain the recovery limit and permit viewing existing history. How the user resolves an indefinitely unknown operation without risking a duplicate remains a product/security decision. Protected feedback page modification requires an exact new SHA and separate approval. App reinstall cannot recover a missing marker without an independently approved server-side discoverability protocol.

This is not a production contract or implementation approval. Process termination timing, atomic durability across Android process death and concurrent WebViews, response loss, database races and local storage protection require actual platform/security evidence. Do not claim a new UI, route, migration, device acceptance, or data-retention policy exists.

## Owner-approved nonproduction investigation and current implementation

Owner explicitly approved design and tests for a nonproduction candidate storing minimal operation metadata and an authenticated read-only query, without feedback answers or credentials. This does not approve a final retention policy or protected-page changes. The current `feedback_recovery_candidate.py` is a **not mounted, internal service candidate**: it returns `record_present_unverified`, `deleted` or `unknown` after checking owner/key/event/music/source and persisted session/task association, and uses `no_autoflush`. It does not establish that a discovered record matches the unavailable original body, and it does not expose an HTTP endpoint or save a local marker. Database errors are not translated into success. No migration or database uniqueness change is introduced. The current tests do not cover full multi-process crash or Android durability; the cross-process issue remains open.

## Completed independent engineering

The former shared 256 unresolved-save capacity was reproduced allowing one owner to block another. The process-local map is now partitioned by owner, each with the same fail-closed capacity; no unresolved item is discarded. This removes the single-owner cross-owner quota failure, but the number of distinct owner maps is not globally bounded; adversarial resource consumption needs separate rate/resource controls. It does not create crash recovery.

## Separate USB test-server candidate

`tools/dev/usb_guest_library.py` creates or resumes only a specifically marked runtime under the external local evidence root. It uses an isolated SQLite database, local test signing key, loopback-only server, restrictive route allowlist and socket/subprocess audit guard; no Provider credentials are loaded. The first synthetic Guest gets a restored WAV fixture explicitly titled as a test rather than generated music. Local loopback checks verified Guest creation, owner isolation, WAV MIME/content and generation denial; an actual server-process stop/resume retained the same test Guest, and an intentionally altered test signing key was rejected. The test processes were stopped. Historical analysis fixture is incomplete, crash recovery UI is not wired, and this is not Android acceptance. The script must not be used with any existing user database or as a production server.

Guarded local results: frontend full 725 passed, feedback specialty 88 passed, H5 build and 109 static hashes passed, Android-context ASGI journey passed. A disposable local MySQL 8.0.44 over verified TLS checked owner isolation and tombstone for the unmounted read candidate; it did not test cross-process client crash recovery. An independent review identified the initial autoflush issue; a regression reproduced it and `db.no_autoflush` fixed it. Actual Android, persistence on OS kill, production databases and Provider calls are NOT RUN.
